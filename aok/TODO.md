# AOK VM: what is open

One entry a subject, newest thinking first within it; moved here from iSH-AOK's `docs/TODO.md` on 2026-10-14
with the rest of the project. "The user" is the maintainer; "the plug-in" is the AOK gadgets engine in
emkey1/qemu; "the Air" and "MBP5" are the two Macs it is built on (the Air signs, MBP5 cross-builds QEMU).

- **x87 in the engine: done 2026-10-14 (emkey1/qemu 7edd35f, 6298205); what is left of it.** The engine's x86 front end runs the x87 as gadgets from aok-gadgets' `x87/` (the same source as iSH-AOK's JIT): both PC guests pass iSH-AOK's 167,517 hardware answers (`bench=x87kat`; QEMU's own x87 misses 59,159 of them), the gate's transcripts are unchanged, and n-body compiled for the x87 costs 39 G cycles where QEMU's engine needs 107 G (`nbody87`, 32-bit guest). Left: (1) `fninit` and the environment forms (`fldenv`, `fnstenv`, `frstor`, `fnsave`, `fxsave`, `fxrstor`) are still QEMU's helpers, which is right for softfloat's modes but means a guest kernel's context switch leaves a stream twice; QEMU's `fxrstor` also keeps the image's ES bit where hardware recomputes it. (2) The last-instruction pointers (`fpip`, `fpdp`, `fpcs`, `fpds`, `fpop`) are not written by the gadgets: an `fnstenv` after a gadget shows the pointers of the last x87 instruction QEMU ran. A handler that looks for the faulting FP instruction there (Windows' does) would be misled; it costs three instructions a gadget in `x87_wait`, the word already has the instruction's offset. (3) The decode tables (which gadget for which opcode and ModRM) are written twice, in iSH-AOK's `jit/gen.c` and in `target/i386/tcg/aok/translate-x86.c`: a header in aok-gadgets would make them one. (4) MMX is still QEMU's, and shares the registers. (5) Not run on a device yet: `aok/ios-app/x86-device.sh` runs `x87kat` there too now.

## Open

- **Three repositories since 2026-10-14, two of them private: what waits for them to be public.** This one (the app), emkey1/qemu (the engine, public) and emkey1/aok-gadgets (the gadget sources iSH-AOK and the engine both build, private). While aok-gadgets is private, iSH-AOK and the QEMU fork hold copies kept in step by its `tools/sync.sh`; once it is public they can take it as a submodule and the copies go. The engine is named here by commit in `aok/ENGINE`, not as a submodule, for the same reason in the other direction: nothing is gained by one until the engines are built from this tree by Xcode (the "AOK VM from Xcode" entry). iSH-AOK keeps `tests/bench-utm/utm/vm-update.sh`: installed machines fetch it from that address, and what it installs is iSH-AOK's `/AOK/tools`.
- **The QEMU fork's RISC-V pair table is behind the shared one.** iSH-AOK remade its pair list from seven workloads (its 933fb5d77, now aok-gadgets' `riscv64/pairs.h`); the fork still has the list of 7db3de6c. Taking it (`scripts/aok-gadgets-sync.sh` there) changes which pairs the RISC-V front end fuses: rebuild, run the RISC-V gates (one CPU and four, pairs on, off, forwarding off), and time it with `aok/cyc4.sh`.
- **x86 on the M4 iPad, 2026-10-14: the gates pass and the six workloads are timed; the A10X has run nothing.** `aok/ios-app/x86-device.sh` on the M4: `check,fptest,memtest` and `x86test` identical to the Mac's `QEMU_AOK=0` transcripts for the 64-bit and the 32-bit guest, and the workloads in host cycles, QEMU's engine against the gadgets, two rounds (x86-64: CoreMark 11.63 -> 5.01 G, n-body 9.40 -> 5.56, Python 35.31 -> 11.05, xz 11.84 -> 4.89, sha256 4.43 -> 2.45, awk 35.62 -> 15.34; 32-bit: 15.05 -> 5.64, 11.06 -> 5.93, 59.19 -> 18.58, 22.12 -> 8.56, 8.01 -> 3.42, 20.11 -> 7.47). - **Games in the "Devuan Ultimate" VM: what runs on an M4 iPad as of 2026-10-13, and the five that have no GPU path.** Seen on the M4 over ssh, each with a grim picture or a number: Freedoom's timedemo on virgl 184 fps; Beneath a Steel Sky (ScummVM) on virgl, its intro on screen after ~55 s; Warzone 2100 on Vulkan (venus on UTM's MoltenVK), its main menu; sound, as far as the guest and the host log can say (aplay and speaker-test without error, a spice playback stream; whether it is heard is the user's to say); the pointer-device storm gone (3 switches in a session, was 2783). **Not working: the fixed-pipeline OpenGL games (Neverball, Armagetron, Chromium B.S.U., Blobby Volley, Trigger Rally).** Two GPU paths, both dead under UTM: (a) virgl -- UTM's virglrenderer sits on ANGLE (GLES 3.0) and the vertex shader it writes for them declares an input array, which ESSL forbids ("'in' : cannot declare arrays of this qualifier", "Dropping rendering due to missing shaders": a black window and a healthy frame count); (b) zink on venus -- every one fails at its first pipeline, `vkCreateGraphicsPipelines` VK_ERROR_INITIALIZATION_FAILED, because the Metal shader UTM's MoltenVK (utmapp/MoltenVK 05604465, not iSH-AOK's fork) makes for zink's bounds-checked uniform block does not compile: `constant uint* uniform_0_32BufferSize = &spvBufferSizeConstants[9];` and then `uniform_0_32BufferSize / 4u`, a pointer divided by an integer; the venus ring then goes fatal and the game aborts or hangs in "stuck in tls ring seqno wait" (it takes SIGKILL). iSH-AOK's own zink runs the same games on the same GPU with the same Mesa, so its MoltenVK or its vkr does something this one does not; which, is not known. Until one path works setup-games.sh leaves those five in software on a VM (Blobby: 5.5 fps on the M4) and `--zink` opts in. - **The QEMU plug-in's x86 front end (qemu-aok 05421d9, 2026-10-14): what it has, and what Windows XP on an iPad still needs.** Long mode's 64-bit code and 32-bit flat protected-mode code are gadget streams (`target/i386/tcg/aok`; aok/docs/engine-study.md, section 12): 1.7x to 3.5x fewer host cycles than QEMU's threaded interpreter in both guests, every gate identical to it (`aok/x64/x64gate.sh` on MBP5: one CPU, four, four under MTTCG, both guests), and the kernel-patching guest that used to die survives (`poke`, `x64load.sh`; the cause was QEMU's own gap between a code store's invalidation and the store, fixed for both engines in qemu-aok 4f86691). The VM app has the engine as its x86_64 and i386 QEMU, with "AOK x86-64 Console" and "AOK x86 32-bit Console"; both ran in the simulator. Next, in the order it pays: (1) **Windows XP has not been tried**: UTM's gallery has only a settings template, and the installation disc is the user's to supply. ReactOS, an NT-class system, stands in and reaches its desktop on the engine (the ReactOS entry above); it has not been run with the counters below yet. What XP adds to what Linux exercises: a BIOS boot through real mode (QEMU's), far more 16-bit-operand code (`66`-prefixed `adc`/`sbb`, pushes and pops are still QEMU's, and each one ends a stream), x87 everywhere, `sysenter`/`int 2e`, code and data sharing pages (with several guest CPUs each store into such a page now costs a turn of the main loop: measure it there). The first run should be with `QEMU_AOK_STATS=2` and `x64/classify.py LOG 40 32`, which ranks the instructions that hand a block back to QEMU. (2) **x87**: done since, as gadgets (the x87 entry at the top); MMX is still QEMU's. (3) Single-precision SSE on the host's FP unit, as doubles have. (4) "Precise" self-modifying code: a store into the block that is running does not stop that block (QEMU's does); nothing has needed it yet. (5) **On devices**: neither iPad has run an x86 guest. The A10X has the app but with the engine of before the fix; the M4 was not connected. `aok/ios-app` knows the labels `x86_64` and `i386` (its QEMU is built with the target since 2026-10-14) for the gates and the six workloads there.
- **The QEMU plug-in's AArch64 front end (qemu-aok 8871044, 2026-10-13): what it has and what is next.** An arm64 Linux guest (`-M virt -cpu cortex-a72`) runs with 99.9% of its blocks as gadget streams -- integer, loads and stores, branches, system registers, exclusives, and the base FP and Advanced SIMD run on the host's FP unit -- 2.1x to 3.4x fewer host cycles than QEMU's threaded interpreter on the Mac (aok/docs/engine-study.md, section 11). Done since (2026-10-13): UTM SE is built with both engines and is on both iPads with "AOK ARM64 Console" and "Devuan Ultimate ARM64" (aok/utm, `ARCH=aarch64`); the M4 passed every gate in the test app and is 2.2x to 3.2x faster than QEMU's engine; in the simulator the Devuan machine boots through UTM and shows its desktop. Next, in the order it pays: (1) **on the devices**: the user's tap on each machine on the M4 (does the desktop show, are the Vulkan device and sound there as on RISC-V); and **the A10X has run nothing** -- its FP unit is the oldest we have (the thunk tables hold encodings it lacks; the translator only selects base ones, AES/PMULL by QEMU's cpuinfo, SHA and CRC32 by sysctl): `aok/ios-app/run-device.sh <bip> aarch64-check-1 1 check,fptest,memtest,simdtest 900` when it is unlocked, then compare as for the M4 (study, section 11). (2) Done 2026-10-13 (qemu-aok 734639c): `ld1`/`st1` and the other structure loads and stores, and `ldpsw`; QEMU's code is entered about a hundred times in a boot and the check programs, and the M4 passes the gates with it. Not measured again: the Devuan desktop's count, which was 6.4 million. Still QEMU's: the LSE atomics. (3) **Fused pairs**: `jit/guest-arm64/pairs.h` and a host-gadgets list as for RISC-V; the translator already tracks whether the host's flags are the guest's. (4) **CPUs newer than the base**: with `-cpu max` the guest is correct but barely faster -- pointer-authentication hints (10,400 blocks begin with one), `br`/`blr`/`ret` under BTI (8,700), LSE, and LSE2's alignment rule are all QEMU's. UTM's default CPU for arm64 is cortex-a72, which has none of them. (5) Exclusives and system registers are a C call each; `mrs daif`/`msr daif` and `ldxr`/`stxr` could be gadgets with a fast path. Gates: `~/aok-vm-bench/a64run.sh` and `a64cmp.sh` on MBP5 (`check,fptest,memtest` at 1 and 4 CPUs and with `A64_CPU=max`, `a64smp.sh` for boot hangs, `simdtest` against `logs/a64/jit-simd.log`, which is stock QEMU's JIT: the threaded interpreter is wrong there, next entry).

- **tctiSH's threaded interpreter (TCTI) computes three AArch64 SIMD instructions wrongly; unreported.** Found 2026-10-13 by aok/bench/simdtest.c: `cmlt #0` and `cmle #0` on 8-, 16- and 32-bit lanes and `sshl` on 16- and 32-bit lanes (18 of 24,576 encodings in the twelve buckets that differ; e.g. `0e20a820`, `4e60a820`, `4e634420`). Stock QEMU 11.0.3's JIT, real hardware (the same guest under HVF) and the AOK gadgets agree with each other; TCTI differs. UTM SE ships TCTI, so its arm64 guests presumably compute these wrongly too (not tried there). - **`docs/CREDITS-aarch64.md` and the QEMU fork: which arm64 files may go there.** The arm64 engine's `gadgets.h`, `math.S`, `control.S`, `simd_arith.S`, `simd_misc.S`, `simd_shift.S`, `crypto.S` and much of the SIMD decoding in jit/gen.c are adapted from OpenMinis/ish-arm64 (GPLv3). QEMU is GPLv2, so none of it was copied into qemu-aok: the fork has `frag.h` and `alu_spec.S` (this fork's own) and its own FP/SIMD. If more of the arm64 engine is ever to be shared with the QEMU fork, it needs either OpenMinis' agreement to GPLv2 (their fork carries iSH's LICENSE.md, which grants it for contributions after 2020; whether they read it as covering theirs is theirs to say) or a rewrite. `scripts/aok-gadgets-sync.sh` in qemu-aok copies only the two files.
- **The pair-fusing pass exists twice: `jit_pair_fuse` (jit/gen.c) and `aok_gen_pair` in the QEMU plug-in (qemu-aok, accel/tcg/aok.c).** The gadget sources are shared (506bf387d the ALU family, 7db3de6cd loads, stores and branches; aok/docs/engine-study.md, section 10); the pass that picks the fused gadget was ported by hand on 2026-10-12 because jit/gen.c had other sessions' uncommitted work in it. Proposed: move the table lookup and the stream rewrite (replace the first gadget's word, drop the second's, pick the forwarding variant when the second's operand names the register the first wrote) into a small C file with no AOK types in its interface, which both trees compile, and have `tools/check-shared-gadgets.sh` build it standalone.
- **The QEMU plug-in's translator does not fold the idioms AOK's does, so the pairs that name them never occur there.** gen.c folds a shift pair (`sll_srl`, `sll_sra`: gen_riscv64_try_after_slli), a shift and an add (`sll_add`), a constant or bit test and its branch (`b<cond>_ri/_ir`, `andi_beqz/bnez`: gen_riscv64_try_li_branch, _try_andi_branch) and an add with the load through it (`add_l*`, memory.S, not a shared body yet) before the pair pass runs. The plug-in assembles all of those gadgets (shared sources) and selects none: qemu-aok target/riscv/tcg/aok/translate.c decodes one instruction a step and has no look-ahead. Needed there: a peek at the next instruction in the same page (and `n_insns + 2 <= max_insns`), the 16-bit forms of the second instruction expanded (c.srli, c.srai, c.add, c.beqz, c.bnez), two `aok_gen_insn_end` calls for a folded step. `sll_add` and the branch idioms are in several of the most frequent pairs (`sll_add+lhu`, `and_rr+sll_add`, `sll_add+ld`). Also not taken: pairs that begin with `auipc`, which is the plug-in's own `pcrel` gadget because QEMU's blocks are position independent, where AOK's is `mov_const`.
