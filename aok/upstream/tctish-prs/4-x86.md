**Title:** AOK gadgets: x86-64 and 32-bit x86 front end (4/4)

**Base:** `tctish-edition` · **Head:** `emkey1:pr/aok-x86` · **Depends on** #… (core); the last three commits are this PR's own.

---

`target/i386/tcg/aok`, in the x86-64 target: a front end for the AOK gadget translator (see #…). It translates long mode's 64-bit code and 32-bit protected-mode code with flat segments (a 32-bit system and its programs, and a 64-bit system's 32-bit programs). Real mode, 16-bit code and virtual-8086 mode stay TCG's. A 32-bit guest is run by `qemu-system-x86_64`; the i386 target has no front end.

## Commits

1. **`target/i386: #GP for MXCSR's reserved bits, #UD for encodings that do not exist`**: TCG corrections found by the vector tests, useful without the rest. `LDMXCSR`, `FXRSTOR` and `XRSTOR` raise #GP for reserved MXCSR bits (and load nothing); SHA-NI instructions with a 66/F2/F3 prefix and the register forms of `MOVLPD`, `MOVHPD`, `MOVNTQ` and `MOVNTDQ` are #UD.
2. **`target/i386: AVX-512's state, for an engine that computes AVX-512`**: XSAVE/XRSTOR of the opmask, ZMM_Hi256 and Hi16_ZMM components, XSETBV taking the three together, `HF_AVX512_EN`, and VEX writes zeroing to bit 511. Inert under TCG alone, which offers no AVX-512 and so cannot enable these XCR0 bits.
3. **`target/i386: an AOK gadgets front end for x86-64 and 32-bit x86`**: the front end.

## How

- **Operands** are byte offsets into `CPUX86State` (`ah` is `al`'s plus one). New fields: `aok_zero` (an absent base or index), `aok_tmp` (where a rarer form's memory operand is loaded so the register form's gadget serves it), and `aok_vstage` (the vector frames' staging).
- **Flags are QEMU's lazy ones.** A gadget stores `cc_dst`/`cc_src`/`cc_op` as TCG's code would, so an exception or a TCG TB finds them right; the translator also tracks what the host's NZCV says of them, so a `jcc`, `setcc` or `cmov` after a `cmp` tests the host's flags directly. Flags nothing reads before the next instruction that sets them all are not computed (looked ahead within the TB; retranslated if that fails).
- **Memory** goes through the softmmu fast path, with a second try on the entry's addend for an access that is only unaligned. A read-modify-write probes for writing first, so a fault restarts the instruction. Under `CF_PARALLEL` every memory gadget has the barriers x86's ordering needs, and a `lock` prefix is cputlb's atomic helper.
- **In C**, one call each: one-operand `mul`/`div`, double shifts, string instructions (`rep` page by page on host memory), `cmpxchg` and its kind, `pushf`/`popf`, `cpuid`, `rdtsc`, port I/O where the CPL may; and the kernel's fast paths through the helpers TCG calls (`iret`, `syscall`/`sysret`, `mov` to and from `cr0`/`cr2`/`cr3`/`cr4`, `invlpg`, `clac`/`stac`, `xsave`/`xrstor`), ending the TB in the main loop wherever TCG ends it.
- **SSE:** moves and integer operations as one host instruction each. Floating point is VEX's frames, which are x86's where QEMU's softfloat helpers are not (which NaN, `MINPS`/`MAXPS` under DAZ, `RCPPS`'s table, flags); doubles try the host's FP unit first where it is exact.
- **x87:** iSH-AOK's integer x87 (`shared/`). It gives every one of iSH-AOK's 167,517 known answers recorded on an AMD Ryzen; TCG's softfloat x87 misses 59,159 of them (stack faults, denormal reporting, C1, and `fsin`/`fcos`/`fptan` computed as doubles).
- **VEX and EVEX:** iSH-AOK's frames (`vec/`, and the tables and planners in `translate-vec.c.inc`): AVX, AVX2, FMA3, F16C, BMI1/2, the opmask instructions, AVX-512 (F, DQ, CD, BW, VL, IFMA, VBMI, VBMI2, VNNI, BITALG, VPOPCNTDQ, BF16), GFNI, VAES, VPCLMULQDQ and AVX-VNNI. Masked accesses touch only enabled elements; gathers and scatters are restartable. TCG has no AVX-512, so the CPU offers it (CPUID, XCR0) only where these gadgets run, and an instruction TCG lacks that must be stepped (EFLAGS.TF) or run alone becomes a one-instruction TB here.
- **Which engine:** a PC has no device tree, so the CPUID brand string ends in `(AOK gadgets)`.
- **Left to TCG:** MMX, the x87 environment instructions, `int`, `sysenter`/`sysexit`, debug registers, `cr8`, loads of `ss`/`cs` and far-pointer loads, string I/O, rotates through carry, 16-bit stack operations and addressing, SSE4.2 string compares and CRC32, SHA, and a few more listed in the doc. Not yet anywhere: EVEX in 32-bit code, and EVEX memory operands with a 0x67 prefix (#UD).

The integer core is this tree's own; `shared/SOURCE` and `vec/SOURCE` give the origin and licence of what came from iSH-AOK (`GPL-2.0-only OR GPL-3.0-only`, all of it my own contributions to iSH-AOK; none of upstream iSH's lines).

## Testing

Both guests, one CPU and four:

- the program and memory transcripts (#…, "Testing") are identical to TCG's. The FP transcript's reference is the hardware: TCG's SSE gives two NaN operands the x87's answer rather than SSE's first source, so TCG's transcript differs from a real CPU's; the gadgets' matches the same binary on an AMD Ryzen line for line (370,000 lines with every result);
- `x86test`: integer instructions on awkward and random operands with the flags hashed (`rep` with DF set, `repne scas`/`repe cmps`, `loop`, `cmpxchg8b`, rotates whose flags are read, segment pushes and loads, every condition after every kind of flag-setting instruction): identical to TCG's;
- `x87kat`: iSH-AOK's 167,517 x87 known answers from an AMD Ryzen, all passed, three times over in one boot;
- iSH-AOK's 35 vector test programs (SSE to SSE4.2, VEX, EVEX, MXCSR, undefined encodings), with answers from a Ryzen or Intel's SDE: all pass, including 20,000 AVX-512 forms and 61,440 EVEX encodings; and a debugger's single-step through AVX-512 code;
- `poke`: three CPUs in the scheduler while the fourth flips a scheduler static key 3,000 times (the guest that found the store-into-code race fixed in #…).

The transcripts, `x86test` and `x87kat` give the same results on an iPad Pro (M4) and an iPad (A10X), both guests. Builds with `--enable-werror` at each of the three commits; boots both guests and runs CoreMark under both engines.
